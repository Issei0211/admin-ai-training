# Planning Skill (実装計画・タスク分解)

このスキルは、機能追加・修正・リファクタリングなどの開発タスクに着手する際、直接コード変更を行わずに「実装計画書」を作成し、人間（開発者）との合意形成を行うための作業手順書です。

## 目的
* 開発者（人間）とAIエージェントの間で、要件・設計・影響範囲の認識を一致させる。
* コードの一気出し（丸投げ生成）を防ぎ、レビュー・検証可能な粒度にタスクを分解する。

## 実行ルール・制約
1. **指示を受けた段階で、いきなりコード（Railsのソースコード等）を書き始めたりファイルを編集したりしないこと。**
2. 開発者からの依頼内容に対し、まず以下の「出力フォーマット」に従った実装計画（Plan）をテキストで提示すること。
3. 認証方式や gem の選定等、未決定の設計事項がある場合は、メリット・デメリットや複数の選択肢を提示して開発者の判断を仰ぐこと。
4. 開発者から計画内容への承認（「この計画で進めてください」等の合意）を得てから、実際のコード実装ステップへ移ること。

## 出力フォーマット（計画書テンプレート）
開発者からタスク依頼を受けた際は、以下のフォーマットで計画を出力してください。
```markdown
### 1. タスクの理解と目的
- **概要:** [何を実装/修正しようとしているか]
- **目的・背景:** [なぜこの変更を行うのか]

### 2. 影響範囲と事前確認
- **影響を受ける主なファイル・コンポーネント:**
  - 例: `app/models/user.rb`, `app/controllers/sessions_controller.rb` 等
- **前提条件・注意事項:**
  - AGENTS.md の制約事項（Scaffold禁止、RSpecによるテスト作成等）との整合性確認
  - 採択する技術スタック（認証方式等の選定状況）の確認

### 3. 設計方針・選択肢の提示
- **技術選定・アプローチ（未決定事項がある場合）:**
  - 例: gem（Devise等）を使用する場合とRails標準機能（has_secure_password等）で自前実装する場合の比較や推奨案
- **Model / DB:** [テーブル構造やValidation、Associationの方針]
- **Controller / View:** [ルーティングや画面遷移、Session操作の方針]

### 4. 段階的な実装タスク（Step-by-Step）
1. **[Step 1: タイトル]**
   - 作業内容: 
   - 確認方法: 
2. **[Step 2: タイトル]**
   - 作業内容: 
   - 確認方法: 
3. **[Step 3: タイトル]**
   - 作業内容: 
   - 確認方法: 

### 5. 動作確認手順
- 手動確認シナリオ（例: ブラウザでの操作手順、`bin/rails c` での確認方法）
- 自動テストの実行（`bundle exec rspec` によるテストコード作成・実行計画）
```

## 承認後の進め方
- 開発者から「計画を承認する」旨の返答があった場合、原則として [Step 1] のみ、あるいは最小限の単位に絞ってコード生成・編集を行ってください。
- 各Stepの完了ごとに開発者へ動作確認・確認のフィードバックを求めてください。
